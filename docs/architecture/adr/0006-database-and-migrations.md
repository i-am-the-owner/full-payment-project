# 6. Database: PostgreSQL, plain-SQL migrations, integrity in the schema

- **Status:** Accepted
- **Date:** 2026-09-07

## Context

Milestone 2 introduces the persistent data model: users and auth metadata,
recipients, reference data (countries, currencies, corridors), fee rules,
transfer quotes, transfers, transfer status history, webhook events and audit
events. The data is financial, so accuracy and an intact history matter more
than convenience.

## Decisions

### PostgreSQL 14+

Already mandated by the project. We rely on: `gen_random_uuid()` (core, PG13+),
the `citext` extension for emails, generated columns, partial and expression
indexes, `plpgsql` trigger functions, and transactional DDL.

### Identifiers: random UUIDs

All externally-referenced primary keys are `UUID DEFAULT gen_random_uuid()` (v4).
Non-sequential, so ids are not guessable or countable. The human-facing transfer
`reference` is generated by the backend and is also non-sequential.

### Money: integer minor units, never floating point

- Amounts: `BIGINT`, in the currency's ISO 4217 minor unit (see
  `currencies.minor_unit`). `BIGINT` holds ~9.2×10¹⁸ minor units — far beyond any
  realistic transfer.
- Exchange rates: `NUMERIC(24,12)` — exact decimal, **not** `real`/`double
precision`. The `pg` driver is configured to return `BIGINT` and `NUMERIC` as
  strings so values never pass through a lossy JavaScript `number`.
- A test (`test/integration/database/schema.test.ts`) asserts no `%_minor`,
  `%_basis_points` or `exchange_rate` column is a floating-point type.

### Integrity lives in the schema

The database is the last line of defence for financial correctness:

- **Check constraints:** positive amounts, `total = principal + fee`,
  non-negative fees, positive rates, valid enum-like `TEXT` values, method-
  specific required fields on recipients, webhook "processed ⇒ signature
  verified".
- **Foreign keys** everywhere, `ON DELETE RESTRICT` for anything a financial
  record points at (users, recipients, quotes, corridors).
- **Transfer state machine as data:** `transfer_statuses` +
  `transfer_status_transitions`, enforced by a `BEFORE UPDATE` trigger. Illegal
  transitions and any change out of a terminal state are rejected in the
  database.
- **Frozen financials:** a trigger rejects any update to a transfer's amounts,
  currencies, rate, quote link or idempotency key after creation.
- **Automatic history:** a trigger writes `transfer_status_history` on insert and
  on every status change, so no transition can go unrecorded.
- **Append-only tables:** triggers reject `UPDATE`/`DELETE` on
  `transfer_status_history` and `audit_events`; `UPDATE` on `transfer_quotes`
  and `quote_fees`.

### Idempotency

- `transfers (user_id, idempotency_key)` unique → a retried create cannot make a
  duplicate transfer.
- `webhook_events (provider, dedupe_key)` unique → a redelivered webhook is
  rejected.
- `transfers (provider, provider_transfer_id)` unique → one provider transfer
  links to at most one AaminPay transfer.

### Migrations: plain SQL + a small runner

Migrations are `backend/migrations/NNNN_name.sql` files with `-- migrate:up` /
`-- migrate:down` sections (dbmate/tern convention). A ~230-line runner
(`src/infrastructure/database/migrator.ts`) applies them in order, each in its
own transaction, tracked in `schema_migrations` with a SHA-256 checksum so an
already-applied migration cannot be silently edited.

No ORM and no migration framework: plain SQL is the source of truth, which is
the right trade-off for a schema that will be security-reviewed. `pg` is the
only added runtime dependency (needed by the application layer regardless).

## Consequences

- Some business rules are expressed twice (schema + backend). Accepted: the
  schema constraints are a safety net, not the primary validation path.
- Adding a value to an enum-like column is an `ALTER ... DROP/ADD CONSTRAINT`
  migration — deliberately visible.
- Trigger-based history and append-only enforcement mean tests clean up with
  `TRUNCATE` (which bypasses row triggers) rather than `DELETE`.
- If migration needs outgrow the runner, the file format is compatible with
  `dbmate`.
