# AUDIT — codebase vs PROJECT_BRIEF.md

Audited 2026-10-03. Paths are relative to the repository root. Nothing in the existing tree was modified (see "Acceptance criteria" at the end).

## Summary

- Updated 2026-10-03 after the provider-neutral layer. Backend, mobile and web tests all pass (see the latest chat report for counts); backend audit 0 vulnerabilities.
- The backend now runs end to end on a built-in mock provider with no keys: onboarding, quote, recipient, transfer and status to COMPLETED.
- All provider code sits behind one `PayoutProvider` interface; statuses, errors, forms and currencies are provider-neutral, and recipients are stored as summaries only.
- Not yet usable with a real provider: the Wise adapter lacks customer onboarding, currency list, dynamic forms and pay-in instructions; Airwallex and Currencycloud are stubs.
- **Still far from launch-ready**: no pay-in step, no real KYC onboarding, no customer web app, mobile send-money screens unreachable, no real email (see "Fix status").

Rule-by-rule notes for this pass:

- **Secrets ever committed:** none. The repository has no commits and no secret was found in code, config or the web bundle, so there are **no keys to rotate**.
- **Holding customer funds:** the only such code is balance funding (A-01), now off behind the flag. There is no wallet, balance or top-up table.
- **Floating-point money:** no database column or stored value uses floating point (all `BIGINT` minor units, rates `NUMERIC`), so no data migration was needed. The one float boundary is the Wise JSON payload (A-18).
- **Authentication on endpoints:** every `/api/v1` endpoint that touches user data or money already required a bearer token and an ownership check; the provider-verified guard was added on top for money endpoints.

Hardening of status corrections (provider layer pass):

- A transfer recorded as `FAILED` can be corrected only by provider data: a signature-verified webhook or a provider lookup. The single use case that does it requires provider evidence, the repository's non-provider method cannot express any status except `FAILED` or `CANCELLED`, and the database trigger rejects the transition unless the transaction declares a provider source.
- Every correction is written to the audit log as `transfer.status_corrected_by_provider`, with the old and new status, the provider's status and the source.
- There is no admin or customer endpoint that sets a status. Tests cover each of these, including a direct database `UPDATE`.

Data model pass (migrations 0015 to 0017):

- Added `provider_links` (one row per user and provider, with an app-encrypted refresh token and key version), user profile columns, `transfers.funding_method`, UUID idempotency keys for new transfers, `transfer_events` (the status history, renamed in place) and a unique provider event id on webhooks.
- Nothing was dropped. Deprecated and kept: `users.payout_provider`, `users.provider_customer_ref`, `users.provider_verification_status`, `users.provider_verification_updated_at`, `transfers.corridor_id`, `transfer_quotes.corridor_id`, `transfer_quotes.rate_source`, and the tables `corridors`, `countries`, `fee_rules`.
- "Provider tokens encrypted at rest" (Rules check) now applies and passes: AES-256-GCM with `ENCRYPTION_KEY`, versioned for rotation; production refuses to start without the key.

New open questions from this pass:

- Wise has no "delivered" state, so a Wise transfer would end at `SENT` and never reach `COMPLETED`. Decide how the app should present that.
- AlmaPay's own fee (`fee_rules`, seeded at £1.99) is no longer applied; quotes show the provider's fee only.
- The mock keeps quotes, recipients and transfers in memory; they are lost on restart.

Behaviour that changed on purpose:

- A confirmed transfer now ends in `AWAITING_FUNDS` (was `processing`); all statuses use the new upper-case enum.
- The quote and recipient endpoints changed shape: quotes take `targetCurrency`, recipients take the provider's form values.
- Money endpoints return 403 `CUSTOMER_NOT_VERIFIED` for everyone until provider onboarding exists.
- Verification and reset links no longer appear in the log unless `DEV_LOG_MAIL_LINKS=true`.
- An unknown currency is an error instead of being treated as 2-decimal.

## How to run the project

Three independent sub-projects, no shared build. Tooling found on this machine: Node 22.23.0, npm 10.9.8, Flutter at `/home/tryhackme/flutter`, Docker.

| Part       | Stack                                                                                                                       |
| ---------- | --------------------------------------------------------------------------------------------------------------------------- |
| `backend/` | TypeScript on Node 22 (native type stripping, no build step for dev), Express 5, Zod 4, `pg`, PostgreSQL, 11 SQL migrations |
| `mobile/`  | Flutter / Dart, `http`, `flutter_secure_storage`                                                                            |
| `web/`     | Next.js 16.3.4, React 19, Tailwind 4, Vitest (marketing site only)                                                          |
| `docs/`    | 20 markdown files, 10 ADRs                                                                                                  |

```bash
# --- Database (the project's test container; port 5432 and 3000 are used by other things on this machine)
docker start almapay-pg-test            # postgres:16-alpine on localhost:55432, user postgres / password almapay, db almapay_test

# --- Backend
cd backend
npm ci
export DATABASE_URL=postgres://postgres:almapay@localhost:55432/almapay_test
export JWT_SECRET=dev-only-insecure-secret-change-me-0123456789
export DEV_LOG_MAIL_LINKS=true          # dev only: shows email verification links in the log
# PAYOUT_PROVIDER defaults to mock: no provider keys are needed
npm run db:migrate
PORT=3999 node src/main.ts              # `npm run dev` also works; default port 3000 is taken here
npm run typecheck && npm run lint && npm run format:check
npm test                                # integration tests need DATABASE_URL
npm audit

# --- Web
cd web
npm ci
npm run typecheck && npm run lint && npm test && npm run build
npm run dev
npm audit

# --- Mobile
cd mobile
export PATH="$PATH:/home/tryhackme/flutter/bin"
flutter pub get --enforce-lockfile
flutter analyze && flutter test
flutter run --dart-define=ALMAPAY_ENV=development   # expects the backend on http://10.0.2.2:3000
```

## Questions for me

1. **Provider model.** Which provider and which product are you actually onboarding with? The answer decides A-01 to A-03. For example, the code assumes a Wise partner account that funds from its own balance, which is the opposite of the brief.
2. **Pay-in.** How should the customer pay: a bank transfer to provider-issued details per transfer, or a balance the customer holds at the provider?
