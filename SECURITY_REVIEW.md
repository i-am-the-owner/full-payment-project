# AaminPay security review

Date: 2026-10-03. Scope: `backend/`, `mobile/`, `web/` and their configuration, as they are now. Read first:
`PROJECT_BRIEF.md`.

**Result: no critical item is OPEN.** Fourteen weaknesses were found and fixed (section 2). What remains OPEN is
listed in section 3 with the decision or outside service it needs. Everything marked PASS or FIXED has an automated
test unless the note says otherwise.

Tests at the end of this review: backend 469 unit + 170 integration (169 pass, 1 skipped: the opt-in Airwallex
sandbox test), mobile 101, website 24. Lint, type-check, format and build are clean in all three. `npm audit`: 0
vulnerabilities in the backend and in the website's production dependencies.

**What this review is not.** It is a code and configuration review plus tests. Nothing was tested against a real
provider, a real production environment or real certificates, and it is not a penetration test. See section 4.

### 4. Input, output, injection

| Check                               | Status | Notes                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Schema validation on every endpoint | PASS   | Every JSON body, query and path parameter uses a strict Zod schema (no `z.object`, no pass-through anywhere in `src/interfaces`), so unknown fields (mass assignment) are refused. Body limit 32 kB. The webhook endpoint takes a raw body that must carry a valid signature.                                                                                       |
| SQL injection                       | PASS   | All SQL is parameterised. The only two interpolations are constant fragments written in code. Injection strings sent through login, recipient, query and path inputs leave the database intact (tested).                                                                                                                                                            |
| XSS / output encoding               | PASS   | The API returns JSON. The only HTML it serves is two tiny script-free pages (onboarding callback, dev mock identity page); reflected values are escaped (tested) and every response carries `default-src 'none'`. The website is React (escaped by default); its one `dangerouslySetInnerHTML` is a JSON-LD block built from static data.                           |
| CSRF                                | N/A    | The API uses bearer tokens in the `Authorization` header and sets no cookies, so a browser cannot be made to send credentials by another site. **When a customer web app with cookie sessions is built it will need SameSite cookies and CSRF tokens** (O-14).                                                                                                      |
| SSRF                                | PASS   | The server never fetches a URL a user (or a webhook) supplies. Provider base URLs come from configuration; the onboarding page URL is returned to the app, never fetched by the server. A webhook containing internal addresses is just rejected (tested).                                                                                                          |
| Open redirects                      | FIXED  | The provider's identity-page URL is checked before it reaches the app: `https` only, no credentials, no IP address, and on a host in `PROVIDER_REDIRECT_HOSTS` (S-04). The onboarding callback never redirects. The dev identity page only links to this backend's own callback (tested with 6 attack URLs). The mobile web view also refuses non-https navigation. |

## 4. What I did not check

- Real provider behaviour (Wise, Airwallex, Currencycloud): everything provider-facing is tested against fakes and the mock.
- A deployed environment: proxy and TLS configuration, firewall, container and host hardening, backups.
- The mobile app on a device (jailbreak/root behaviour, screenshots, clipboard use on the pay screen: the copy
  buttons write bank details to the clipboard, which other apps can read; that is a usability trade-off for you to accept).
- Social engineering and operational controls (who holds admin access, how keys are handled by people).

## 5. How to re-run the checks

```bash
cd backend
npm run lint && npm run typecheck && npm test            # needs DATABASE_URL for the integration tests
npm audit
node scripts/scan-secrets.ts src scripts migrations .env.example dist ../mobile/lib ../web/src ../web/.next/static
npm run user-data -- export --user someone@example.com   # UK GDPR export
cd ../mobile && flutter analyze && flutter test
cd ../web && npm run lint && npm test && npm audit --omit=dev
```

Security tests are in `backend/test/integration/security/` (cross-user access, suspension, fraud alerts, CORS,
headers, errors, injection, redirects, authentication, log leaks, privacy), `backend/test/unit/security/`,
`backend/test/unit/config/` and `backend/test/unit/infrastructure/providers/mtls-transport.test.ts`.
